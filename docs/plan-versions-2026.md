# The plan: every version of the year from 2026-01-01 (decided, not built yet)

Status: the decisions below were made together; only the two items marked **built** exist (described in [exporter.md](exporter.md)). Nothing of the plan has been run yet. The base of today is described in [versions.md](versions.md).

**Found out (tried):**
- **Headless works (built):** `export_units.ps1 -Headless` starts `spring-headless.exe` instead of `spring.exe`: no window, no dialog box (an installed-game dialog such as "Dependent archive ... not found" cannot block it), 30 s instead of 45 s. The data are the same as from the window; only the loot boxes differ (chance, see [versions.md](versions.md)).
- **The widget list (built):** the widget handler of older game versions (test-29183: `luaui/barwidgets.lua`, line 541) does not start a *new* user widget by itself: the game ran, but `unit-export.lua` was never loaded and the export waited until the timeout. A newer game turns it on itself. So `export_units.ps1` writes `LuaUI/Config/BYAR.lua` into the sandbox before the start (`order = { ["Website Unit Export"] = 12345 }`, `allowUserWidgets = true`); then every version loads the widget.
- **The version of 2026-01-01** is test-29183-32bb796. Its package is 29 MB of files that the installation did not have yet (4 s); the export has 1678 units (43 s). Against test-31836 (the newest) 31 units are gone (15 real ones, the others their Scavenger copies; mostly the Scavenger "s" variants `armsaap`, `armsack`, `corsalab` ... and `armminebomber`) and 16 are new (`corobligator`, `corves`, `legapollyon`, `corhltfus`, Raptor turrets ...).
- **The versions are on the branch `stable`** of the Beyond All Reason repository, not on `master` (test-31820 is the commit "Release 2026.11.04-1" there). The rapid list also holds builds of other branches: only commits that are on `stable` count. From 2026-01-01 to test-31836 there are 333 versions (332 steps).
- **How often something changes** (files of the repository between two versions, trees only): values (`units/`, `unitbasedefs/`, `weapons/`, the `*_post.lua` of `gamedata/`) in 133 of the 332 steps, models, textures or scripts in 71, one of the two in 152, neither in 180. Typically 4 files (median); a few steps touch hundreds (moves, formatting; the largest 895). 993 different unit files were touched in the year. These are upper bounds: whether a file changes a *value* or a *picture* only the export shows. Expected: at most about 150 diff files of 1 to 5 KB (under 1 MB together) and, as a rough guess, 2 to 10 MB of pictures besides the 27 MB of the base.

**Decisions:**
1. **Base version: test-29183-32bb796 (2026-01-01).** Its full reduced file and all its pictures (about 10 minutes of rendering, about 27 MB) are made. The base of today (test-31820) becomes an ordinary diff version of the chain; all diff files are made again from it. The pictures of the old base leave the working tree (they stay in the history of Git: about 27 MB more for good).
2. **Which versions, which dates: from the Git clone, not from the GitHub API.** A bare clone of the repository without file contents (`git clone --bare --filter=blob:none`, 35 MB, in a cache folder outside the repository, kept up to date with `git fetch`) gives the commits of `stable` and their dates. The versions are the `byar:git:` entries of the rapid list whose commit is on `stable` and whose date is from 2026-01-01 on. The date of a version is the commit date from the clone (the API of GitHub is not used, it answered with 503 and 504 often).
3. **The status is one field: `checkedUpTo`** in `versions.json` (the name of the newest version looked at). Versions are always done in order, so everything up to it is done, with a diff file or without a change. It moves after every version, also the skipped ones, so an aborted run goes on where it stopped. It replaces the list `unchanged`. `versions.json` lists the base and the versions that have a diff file; `base: true` marks the base.
4. **Prefilter with Git (nothing is downloaded or started for a skipped version).** For every step `git diff --name-only <version before> <version> -- <paths>` on the clone (all 332 steps take about 35 seconds). No file of the *value paths* or the *look paths* changed: the version is skipped (`checkedUpTo` moves on). Value paths: `units/`, `unitbasedefs/`, `weapons/`, `gamedata/` (the unit and weapon definitions with their `*_post.lua`, `armordefs.lua`), `language/` (names and descriptions are in the data), `common/`, `modoptions.lua` and every gadget that changes unit definitions at run time (`luarules/`). Look paths: `objects3d/`, `unittextures/`, `scripts/`. **The list must be complete:** a missed path loses a change. Before the run it is checked against the versions that are exported already (test-31465, test-31479, test-31820, test-31836, test-29183: a step that the filter would skip must show no change in the exports) and with spot checks (some skipped versions are exported all the same and compared); the switch `--no-prefilter` exports every version.
5. **Versions that change only the look** (a path of the look paths, none of the value paths): the game is not started. The values are the ones of the version before; the package is downloaded for the fingerprints (`render_unit.picture_fingerprints` needs only the pool); the units whose fingerprint changed get a diff entry (the reduced entry of the version before, `ownPicture`) and a new picture.
6. **Every other version (a hit):** download the package (`pr-downloader`), export it (headless, its engine, section "Engines"), diff against the state of the version before, render only the pictures that changed. **Which units changed the comparison of the exports decides**, not Git: Git only decides whether a version is exported (a file of the repository does not tell which units a change reaches: shared modules, Scavenger copies, post-processing); the names of the changed files may be shown as information later. The game start (about 30 to 45 seconds, always all units at once) is the expensive part and cannot be limited to some units; the pictures are already the minimum (only the changed fingerprints are rendered).
7. **Engines: every version, the base too, is exported with the engine that was meant for it.** The date of a version (from the clone) decides. The history of the engine is in the launcher configuration `dist_cfg/config.json` of the repository `BYAR-Chobby` (every commit names the standard engine and, as a second entry, a test engine); a table "engine from, until" is made from the commit dates of that file (`exporter/engines.json`, made by a script from a clone of that repository; the date is an approximation of the day the players changed, nothing better is known). Read so far (to be checked against the file when it is built, which entry of a commit is the standard one): `recoil_2025.06.12` at the start of the year, `2025.06.19` from about 2026-02-20, `2025.06.24` from about 2026-05-26, `2026.06.11` and `2026.06.12` in July, `2026.07.04` from about 2026-08-05; `2026.09.01` / `2026.09.02` are so far only test engines. About seven engines, each about 24 MB. The engine is loaded by `pr-downloader --download-engine <version>` and started with `export_units.ps1 -Engine` (`pr-downloader` unpacks into `<data>\engine\windows64\<version>`, so `-Engine "windows64\2025.06.12"`; decided: the engines lie in an own cache folder next to the project (not in Git), the installation stays untouched; a version without an engine of its own uses the standard engine of the newest Chobby entry). `versions.json` names the engine of every version (`engine`). Tried: test-29183 with `2025.06.12` and with `2026.07.04`: the same data except `armcomboss` (its build time of about 750 billion overflows differently: 750000013312 against -2147483648).
8. **A change of the engine between two versions is controlled:** the version before is exported again with the engine of the new version (about 40 seconds, about seven times in the year). The diff compares two exports made with the **same** engine, so it holds only changes of the game. What differs only because of the engine is not recorded as a change; the units are named in `versions.json` (`engineOnly`: unit, the old and the new value, both engines) so that they can be looked at. If a number there is grossly wrong (like the build time above), it is corrected by hand and noted there. The run does not stop for these.
9. **A failure stops the whole run.** If a download or an export of one version fails (the game does not start with its engine, no result, a timeout), the run ends with the message and the version is not skipped; the cause is fixed first, then the run is started again and goes on at `checkedUpTo`.
10. **Gone units:** the list `removed` of a diff file is the tombstone (the names of the units that the version no longer has). A unit stays complete in the older versions (values, its picture is in the folder of the version in which it last changed) and is missing from the version in which it was removed on; in the version comparison the selection also offers units that are gone, with the data of the last version that had them. A unit that comes back is new again in the diff file. A renamed unit is gone and new (no link between them). To check at the first real run: a gone unit is shown in the version before and not after; `tests/test_data.py` checks that `removed` names only units that existed before.
11. **The website:** the diff files of all versions come in **one file** `history.json.gz` (the reduced file of the base stays separate) instead of one request per version (up to about 150); the pictures stay in the folders of their versions. The list of game versions is **grouped by month** (`<optgroup>`, for example "2026-03", with the number of versions). Nothing else of the page changes ([website.md](website.md), section "Data").

**Built so far (step 1):** `exporter/git_history.py` (the clone `cache/bar.git`, versions and dates of `stable`, the prefilter with `VALUE_PATHS` / `LOOK_PATHS`; of `luarules/` only `configs`, `gadgets/include` and `Utilities` count: no gadget writes to the unit definitions, checked with `git grep` over `luarules/gadgets`; the result: of 338 steps 112 are skipped, 9 only change the look, the rest is exported), `checkedUpTo` instead of `unchanged` (`reduce_units.py`, the scripts, the tests), `exporter/make_engine_table.py` and `engines.json`, `-Engine` (a full path too) and `-Control` in the scripts, `engine` and `engineOnly` in the diff file and in `versions.json`, `update_versions.py` for the whole chain (`--no-prefilter`, `--keep-exports`, a folder with another base is refused), the tests `tests/test_year.py`. A version that only changes the look is exported like any other for now (the game start is saved only for the 112 skipped ones); not yet built: `history.json.gz`, the grouping by month, the version compare page.

**Order of work:** (1) the prefilter with `checkedUpTo`, the clone, the engine table and `engine` per version, the control export at a change of the engine, `update_versions.py` for the whole chain; (2) the first test (a few versions, in a scratch folder, `--out`), then the run from the base (`update game versions.bat`); (3) `history.json.gz` and the grouping by month, the tests (`tests/test_data.py`, `tests/website_smoke.mjs`) and the documents; (4) commit, push.

## The version compare (a page, planned)

In addition to the unit compare (units side by side, [website.md](website.md), section "Compare") the site gets a **version compare**: the question there is "what changed in the game", not "how do these units differ".

- **The list:** all versions that have a diff file, grouped by month (`<optgroup>`, for example "2026-03"), newest first, each with its date and the number of changed, new and gone units.
- **One version or a range:** a version shows its units; a range (from version A to version B) shows what changed between them in total (the units of B against the units of A, both known from the chain; a unit changed twice shows the sum).
- **A unit in the list:** picture, name, and the values that changed as `old -> new` (metal, energy, build time, hitpoints, DPS, ...), new units marked as new, gone units as gone. Filters: faction, category, which value changed, search by name.
- **From there to the unit compare:** a click on a unit opens the unit compare with the version before and the changed version side by side (what the **Versions** button of the unit compare does today); the unit compare stays as it is.
- **Data:** nothing new: `history.json.gz` (decision 11) has all diffs, the page already chains them (`loadVersions` in `website/app.js`); old and new values come from two versions of that chain.
- **Decided later:** `update_versions.py` uses only the branch `stable` (until the Git clone exists it must not mix builds of other branches).
- **Open:** whether to show the names of the changed files of the Git prefilter as information; how a change of the engine only (`engineOnly`, decision 8) is shown (suggestion: as a note on the version, not as a change of the unit).
- Built together with `history.json.gz` and the month grouping (the order of work above, step 3), not before the year run exists: it cannot be tried properly on one version.
